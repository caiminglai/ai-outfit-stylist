## 1 A 档：公式可直接抄

### 1.1 sRGB → CIELAB(D65)

`colorMetrics.js:32 hexToLab`，测试基线 `#FF0000 → L53.2, a 80.1, b 67.2`。
出处：GB/T 7921-2008（现行，采标 CIE 15:2004 / CIE 142:2001，**非等效 NEQ**）；色空间定义在 **ISO/CIE 11664-4:2019**。
⚠️ 注释里笼统写"ISO/CIE 11664"是**指错分部**：-4 只定义坐标，CIEDE2000 在 **11664-6:2022**（清单第 4 节第 7 条）。

**关键的降质环节不在公式，在输入**：上衣色来自"色名 → 手拍 hex 词表"（`colorMetrics.js:208 _firstColorNameIn`、`:223 resolveColor`），肤色来自 8 个手校准锚点（`:239 SKIN_TONE_ANCHORS`，文件自注"不是文献值"）。所以 ΔE00 算得再准，量的是"两个我编的色块差多远"，只剩**相对差异**可用，绝对值不许对外称测量。

### 1.2 CIEDE2000

Sharma, Wu & Dalal 2004《The CIEDE2000 color-difference formula》Color Res Appl 30(1):21-30，DOI 10.1002/col.20070 ⇒【官方原文】。
实现见 `colorMetrics.js:67`，含 G 加权、hue 象限处理，测试覆盖。

### 1.3 ITA°

ITA° = arctan[(L\* − 50) / b\*] × **180/π**。
✅ 10-08 已修：原写 `100/Math.PI`，整套分档被系统性压低 1.8 倍（白皙 29.0→intermediate，真值 52.1→light）。`backend/test/colorMetrics.test.js` 钉了两条：`(L−50)/b=1` 时恒为 45°；白皙锚点 52.1±0.2 ⇒ 档位 `light`。旧系数会算出 25 而直接失败。
切点 55/41/28/10（以及 brown/dark 用的 −30，通行值 −3【未核实】）出处＝Chardon 1991，数值经 2020 PLOS ONE 转述 ⇒【二手】。
**红线**：ITA 只能用于色卡/测色仪值。Alipour 2026（DOI 10.1111/srt.70374）证明非受控成像下固定阈值 ITA 分型准确率 22.9% ＜ 基线 51.3% ⇒ **绝不能用照片或自拍推肤色再算 ITA**。
`itaClass` 目前只出现在定义与测试两处，**未进顾客端链路**，所以修完线上分数不变。

## 2 上衣贴合分：现在算的是什么、要怎么改

现状（`colorMetrics.js`，10-09 起）：

```js
const WEIGHTS = { hueContrast: 0.45, brighten: 0.35, chromaMatch: 0.2 } // 手拍，未回归
const hueContrast = 0.5 + _clamp01(dHue / 360) // 图形色(衣)对背景(脸)：色相差越大越被偏好
```

10-09 之前第二行是 `const hueSim = 1 - _clamp01(dHue / 180)`（把 Schloss & Palmer 的"和谐"那条用到了"上衣衬脸"上）⇒ 已换成上面这条对比式，权重三个值没动（仍是 C 档手拍）。

现量表现（清单第 5 节；旧口径 10-08 与新口径 10-09 两把尺子都留着，改前改后同尺子可比）：
- 28 条上衣规则里只有 **9 条**能取到颜色出分（其余是款式/场合/Kibbe，`resolveColor` 取不到色值 ⇒ 不出分，属正常）。分母改前改后一样。
- 8 个肤色档 × 9 条色的极差（**旧** `hueSim`）：autumn-f 24、winter-f 23、winter-m 25、autumn-m 11；但 spring-f 4、spring-m 4、summer-f 4、summer-m 4、business-formal 4（SD≈1.1）。
- 极差（**新** `hueContrast`，10-09 现量）：autumn-f 19、autumn-m 17、winter-f 18、winter-m 20、spring-f 6、spring-m 6、summer-f 5、summer-m 6、business-formal 6 ⇒ 均值 11.4。
- 任意两肤色间排序一致性 Spearman（n=9）：**旧** min −0.07、均值 0.40、max 1.00 ⇒ **新** min 0.58、**均值 0.87**、max 1.00。
- 直白结论：秋色/冬季族这条分对"人"敏感，**春夏与浅色商务基本不认人**——分数主要由颜色自身属性决定，不是人-衣匹配。**换对比式没有改变这个结论，反而更强**：`SKIN_TONE_ANCHORS` 八档自己的色相角只跨 49.8°（冷皮）~74.5°（偏黄）共 24.7°（10-09 由锚点表 `atan2(b,a)` 现算），所以"衣对脸的色相分离"对谁都差不多 ⇒ 排序一致性升到 0.87。要真按人区分，得接下面第 1 条剩下的那半（肤色深浅→冷蓝/暖橙偏好方向，`08` §2.1 第 5 条）而不是继续调这一轴。

三个必须修的点：

1. **维度用错（最重要的概念错）**。Schloss & Palmer 2011（PMC3037488，已打开全文逐字核）同一篇里有两句方向相反的结论：`pair preference and harmony both increase as hue similarity increases`（两块色当一个整体时）与 `figural color preference ratings increase as hue contrast with the background increases`（图形色衬背景色时）。上衣衬脸属于**后者** ⇒ 该用**色相分离**而非相似；界面文案"对比越干净越显白"其实与文献同向，**是代码口径不对**，而且现在把两个不该相加的因变量加进了同一个分数。
2. **权重要公开标成产品假设**。0.45/0.35/0.2 没有任何回归依据；`brighten` 一维可以引 Zhang 2025（深色上衣让肤色显得更白，Coloration Technology 142(2):259-271）作为**方向**支持，但仍是产品设定值。等 F7 的标注回归出来才能替换。
3. **和谐分要单列一轴，不许与贴合分相加**。可用指数首选 Nemcsics CHR（DOI 10.1002/col.20700，0–100，锚在人群平均和谐感），代价是要 A32008 色立体与 CIELAB 换算表（付费）。退一步用 ΔH/ΔC/ΔL 的规则式和谐分也行，但必须写明：Kuo 2012（DOI 10.4028/www.scientific.net/AMR.627.524）实测**和谐模型从色样迁移到服装图像上预测力下降**。

## 4 缺测纪律（这条现在被违反着）

**规则**：判据字段没实测 ⇒ 走"没量"分支，返回空对象，规则不命中；**不许**用默认值算出一个看起来像实测的数。

现量对照：
- ✅ 做对的：`computeLegRatio`、`computeWhRatio` 未测返回 `{}`；`colorFit` 无肤色档不出分（有测试 `没有肤色档 ⇒ 一律不给 color_fit`）。
- ❌ 违反的：`computeShoulderRatio`（`profileEnricher.js:203-204`）用 `_safeFloat(shoulder, 38)` / `_safeFloat(height, 162)`，且 height ≤ 0 时直接返回 `{shoulder_ratio:23.5, shoulder_status:'normal'}` ⇒ 每个没量肩宽的用户都会被编出一个 A 档比值，3 条肩宽规则照常出结论。`computeBodyShape`（:85 附近）同样 bust 缺省 84、waist 66、hip 90。
- 根因原来是**采集端缺字段**（10-09 已补肩宽，剩下的缺口见本条末尾）：`app/src/components/PersonalProfileForm.tsx` 的测量区收 `bust/waist/hip/leg_length`（"腿长量髋骨到脚跟"），肩宽除 `shoulder_type` 枚举外，**10-08 已加数值输入项**（`PersonalProfileForm.tsx` 测量区多了"肩宽"一格，提示语写明量两侧肩峰点、不填就不判）。库里 10-09 复量：`body_metrics` 9 行、`shoulder_width_cm` 2 行有值（点验时填的 42），其余为空 ⇒ 采集口通了，数据还没攒起来。

修法（行为变化，需产品拍板）：① 表单加数值肩宽；② `computeShoulderRatio` 未测返回 `{}` ⇒ 后果是没量肩宽的用户那 3 条 A 档肩宽规则不再出结论（这是诚实的表现，不是 bug）。

## 6 档位标注机制

`backend/services/evidenceLevels.js`：`EVIDENCE_LEVELS` + `evidenceOf(key)` 按规则 key 前缀映射档位（例：`['proportion-shoulder','A']`），`LABELS / NOTES / VALUES / DEFAULT_LEVEL / evidenceNote` 一起导出。`recommendEngine.js` 输出 `evidence_level: m.evidence_level ?? null`，兜底 `null`（第 633 行附近），测试要求"每条穿搭都带 evidence_level 字段，A/B/C/D 或 null，不许 undefined"。

⚠️ 两份手抄风险（清单第 4 节第 9 条）：`app/src/components/recommend/EvidenceTag.tsx` 的 `META` 自己复制了一份 A/B/C/D 说明文案，文件头写着"改档位定义要两边一起改"。**目前两份都还点着 GB/T 1335 与 GB/T 10000**——顾客页那段刚从 1335/10000 撤下来，依据说明 tooltip 里还在。改档位解释必须同步这两处。

## 第一：体型与廓形的量化算法

### 1.1 输入

身高、体重、胸围、腰围、臀围、肩宽、腿长，全部取自表单净尺寸。没有插值、没有估算、没有用默认值补齐。缺测字段不参与计算，函数直接返回 `{}`（这条是 `docs/依据/README.md:64`「缺测不出分」那条硬规矩（🟢 10-20 现量改号：本文件出稿时它确实在 `:36`，README 后来插了两行——10-19 有人把它登记成 `:39` 也偏了一行，现号逐条量过＝**L41**））。

BMI＝体重(kg)／身高(m)²，出处 GB/T 31901-2024 附录 A 表 A.2 脚注公式，档位在 `backend/services/bmi.js` 的 `GB_BANDS`。

### 1.2 体型分类＝if-else，不是聚类

`backend/services/profileEnricher.js:80` `computeBodyShape(bust, waist, hip, shoulder)`：（10-19 现量；建这页时写 `:78`，档案侧加了体型词形归一后往下挪一行）

```js
bwDiff = bust - waist
whDiff = hip - waist
if (|bwDiff - whDiff| < 5 && bwDiff > 10)   → 沙漏型 hourglass
if (whDiff > bwDiff + 5)                     → 梨形  pear
if (bwDiff > whDiff + 5) {
    if (shoulder <= 0)                        → body_shape_status: 'unmeasured'（不下结论）
    if (shoulder > hip * 0.45)                → 倒三角型

}
else                                          → 直筒型
```

**关于聚类的直接回答：全仓没有。** 判据＝`grep -rniE "kmeans|k-means|聚类|cluster" backend app` 命中 0 个算法实现（只有无关字面）；而且 `body_metrics` 表实测 14 行，样本量根本不支持聚类。所以「用 K-Means 无监督分出中国人的型」这件事现在是零、短期也不该做。

### 1.4 "视觉修正"逻辑：有，是算出来的方向向量，不是查表映射

不在体型分类里，在 `backend/services/topFitBody.js:265` `bodyDeviation(person, est)`——把身材翻译成一个 −1~+1 的「想要向量」：

```js
groove = min(bust - waist, hip - waist)               // 腰沟
want.waist = clamp((groove - (12+6)/2) / 6, -1, 1)    // 腰线要提多高

diff = hip - bust                                      // 下半身占优程度
want.shoulder = diff > 0 ? clamp01(diff / 8) : clamp(diff / 12, -1, 0)

want.volume = BMI >= 28 ? -1
            : BMI >= 24 ? -clamp01(0.3 + (BMI - 24) / 4)
            : BMI < 18.5 ? clamp01((18.5 - BMI) / 4)
            : 0
want.pattern = want.volume                             // 显胖 → 避横向大图案
if (bmi >= 25) want.pattern = null                     // Ashida 2013：大体型时效应减弱/反转
```

效果上等价于「梨形 → 要提腰线、要提肩线、要 A 字下摆、避大横图案」，但它是连续分数而不是 `if 梨形 then 高腰裤`。

### 1.5 断点在最后一公里（这一条最重要）

want 向量算得出来，**衣服那一侧必须有实测尺寸**（肩宽、胸围、衣长、腰头高）才能对齐。衣服那一侧的数只认衣柜行的四个实测尺寸列（`schema.sql:351`），读取处 `topFitBody.js:494` `describeTop(row, dev)`；没量的轴返回 null、不进归一，**绝不从商品名的中文词里猜**（"宽松""落肩""高腰"那套猜测 10-19 第二阶段已废除，见 §七）。用户衣橱表原来没有这四个字段。

对数公式在 `topFitBody.js:751`：

```js
align = (want, given) => 1 - |want - given| / 2      // 两根都齐才算
总分 raw = Σ(weight_i × score_i) / Σ weight_i         // topFitBody.js:870，只对"有数的轴"归一
```

### 2.2 色度学本身是真的，不是简陋逻辑

### 2.3 当前进决策的打分公式

`colorMetrics.js:1106` `colorFit(skin, topColor, opts)` —— 10-19 **第一阶段·止血第 4 条已把这条分改成两分量**（改前签名是两参 `colorFit(skin, topColor)`、总分只有对比侧）：

```js
hueContrast = hue_applies ? 0.5 + clamp01(ΔHue / 360) : 0.5   // :1381-1383 Schloss & Palmer 图形色(衣)对背景(脸)
                                                              //         任一侧 C*<5（黑/白/灰）⇒ 色相角是 atan2(0,0) 造出来的假数，
                                                              //         这一轴按"没有信息"钉 0.5，不把 45% 权重摊给剩下两轴
brighten    = clamp01(0.5 + (L_肤 - L_衣) / 80)               // :1388  10-23 现量改形状（S1）：中心化 0.5＋分母 80
chromaMatch = 1 - clamp01(|ΔC| / 60)                           // :1389

// 对比侧（衣 vs 脸）——ΔE00 在这里进决策，当**乘法闸门**不当第四轴
gate          = fusionGate(ΔE00)                               // :1390  ΔE00≤6→0.85，≥15→1.0，中间线性
contrastScore = 100 × (0.45·hueContrast + 0.35·brighten + 0.20·chromaMatch) × gate   // :1391-1395

// 呼应侧（衣 vs 衣）——outfitHarmony 的分数按 30% 份额并进总分（HARMONY_SHARE :1262）
score = harmony 有数 ? round(0.7·contrastScore + 0.3·harmony) : round(contrastScore) // :1284
```

两个分量各自回传（`contrast_score` / `harmony_score` / `fusion_gate` / `hue_applies`），报告要拆账或第二阶段要单拎一维都拆得回去；`recommendReportText.js:97` 那一行现在就把两侧都打出来。

### 3.2 成衣放松量怎么从净胸围算：按 BMI 分四窗，不是固定加 10 cm


## 一、为什么"三维样本"这道门靠采数据到不了（四条证据，逐条可复算）

1. **规则那一路永远没有身体维。**`recommendEngine.js:1042-1045` 逐字："身材这一维现在**只认衣柜行的实测尺寸**……规则结论给的是'亮色上衣'这种自由文本，一格实测都取不到"。这是 10-19 第二阶段废除中文猜测时**故意**留下的，⛔ 不许为了凑样本把它改回猜字。
2. **衣橱那一路没有规则维，也进不了反馈表。**`recommendEngine.js:1119` 写 `group_id: null`；`feedback_events.group_id` 是 `NOT NULL REFERENCES rule_groups(id)`（`schema.sql:301`）＋`UNIQUE(user_id, group_id)`（`schema.sql:320`） ⇒ 衣橱卡打的分**没有地方可写**。
3. **前端连控件都不给。**`RecommendationReport.tsx:431` 那句 `{item.group_id > 0 && (...)}` 把整块评分区（👍/👎 与两把星）圈在"必须有规则号"里 ⇒ 用户对着衣橱那件衣服想打分，**页面上没有那两颗星**。
4. **门店模式看不到带尺寸的候选。**`recommendEngine.js:1101` 的 `if (mode === 'personal')` 让衣橱候选只对个人模式开门（实测 store 传 `wardrobe_items` ⇒ `from_wardrobe=0`）；而前端唯一在用的入口是 `/api/recommend/engine`（`api.ts:390`），它**从不注入 `wardrobe_items`**（全仓注入点只有 `routes/wardrobe.js:1337` 一处，前端调 `/api/wardrobe/recommend` 现量 **0 处**）。

⇒ 结论一句话：**能打分的那条路上没有身体维，有身体维的那条路不能打分。** 所以第一步的活不是"引导用户多填"，是先决定样本按什么形状采。你 10-21 在四条出路里选了 **B：衣橱卡开评分通路**（A 商品库加尺寸列＋绑 SKU／C 采样口径降级／D 本轮只做零迁移接线，三条同时作废并记入 §八）。

## 二、`item_feedback`（本阶段唯一一次迁移，加法，不改现有表）

设计取舍：**不动 `feedback_events` 一根手指**。要它支持"人×衣服"得放宽 `group_id NOT NULL` 并重建表（SQLite 不能 `DROP NOT NULL`），风险压在服务器那份被 skip-worktree 钉住的运行库上；新建一张表是纯加法，回滚＝`DROP TABLE`，老库跑 `CREATE TABLE IF NOT EXISTS` 即可。两张表语义不同、不许混用：`feedback_events`＝**这条规则准不准**（人×规则），`item_feedback`＝**这件衣服你穿得怎么样**（人×衣服）。

```sql
CREATE TABLE IF NOT EXISTS item_feedback (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  actor_key TEXT NOT NULL,          -- 'u'||user_id 优先，游客退 's'||session_id（见 §2.1）
  user_id INTEGER REFERENCES users(id),
  session_id TEXT,
  wardrobe_item_id INTEGER NOT NULL REFERENCES user_wardrobe(id),
  occasion TEXT,                    -- 只收 §〇 那五个受控词，⛔ 不新造词
  signal TEXT,                      -- 'useful' / 'inaccurate' / 'rated'，与 ruleFeedback.js:25 同一把尺子
  aesthetic_score INTEGER,          -- 1~5，越界 400（复用 ruleFeedback 的 starValue）
  fit_score INTEGER,                -- 1~5，同上
  rank_snapshot TEXT,               -- 打分那一刻的 rankDims 出账（JSON）
  created_at TEXT DEFAULT (datetime('now')),
  updated_at TEXT DEFAULT (datetime('now'))
);
CREATE UNIQUE INDEX IF NOT EXISTS ux_item_feedback_actor_item ON item_feedback(actor_key, wardrobe_item_id);
CREATE INDEX IF NOT EXISTS ix_item_feedback_item ON item_feedback(wardrobe_item_id);
CREATE INDEX IF NOT EXISTS ix_item_feedback_occasion ON item_feedback(occasion);
```

### 2.1 身份口径（`actor_key` 为什么必须存在）

`feedback_events` 用 `UNIQUE(user_id, group_id)` 能成立，是因为登录态下 `user_id` 必有值（游客由 `ensureGuestUser` 造行）。衣橱这条路的现状不是：`user_wardrobe` 10 行里 `user_id` 只有 **1 行**非空、`session_id` 10 行全有（`collect-census.cjs`）。把 `user_id` 当唯一键会让**所有游客的打分互相覆盖**（SQLite 里 `NULL` 之间不算冲突，反而全变成重复行）。⇒ `actor_key` 在写入口一次算死：有 `user_id` 用 `'u'+id`，否则 `'s'+session_id`，两者都没有就 **400 说破**（不许匿名落库）。这一条与日记的 `session∪user` 并集口径同源（`16` §四），但**这里要的是一个能建唯一索引的单值**，不是并集查询。

### 2.2 写入口契约（`POST /api/recommend/feedback/item`）

1. `wardrobe_item_id` 必填正整数，且这一行必须归这个 `actor_key`（`session_id` 或 `user_id` 命中）⇒ 认不到 **404**，与日记同一档（`16` §四 第 3 条），⛔ 不返回 403（那等于承认这行存在）。
2. 两把星复用 `ruleFeedback.js` 的 `starValue`／`scoreError`：非 1~5 整数 ⇒ **400 说破**，不静默清空。
3. `occasion` 给了就必须是五个受控词之一 ⇒ 否则 400（现量词表见 §〇）；没给就存 NULL。
4. `rank` 走与 `snapshotValue`（`ruleFeedback.js:67`）同一份解析，认不出形状存 NULL；⛔ 但不复用它的"三维全空才丢"那条——本表只认 `color`/`body` 两维，两维全空才存 NULL。
5. `undefined＝这格不动／null＝明确清空` 的既有契约原样继承（`16` §三），一人一衣只留最新一行（覆盖，不叠加），与 `feedback_events` 同一哲学：好评率不能被重复点击灌大。
6. ⛔ **写这一张表绝不许动 `rule_groups.feedback_up/down`**：那是规则的好评率，衣服的分进不去。

### 2.3 快照里到底存什么（这是"三维门"的真正解药）

存 `rankDims` 出账的**在场维**，即 `dims[]` 原样带 `key`＋`score`＋`coverage`，另带 `present`。回归侧从 `present` 里取子集，⛔ 不要求 `rule` 在场——因为衣橱来源的候选结构上就没有规则维（§一 第 2 条），要求它就是要求 0 条样本。

## 三、二维回归口径（`regress-rank-weights.js` 的第二条路）

1. 加 `--source=item`，`DIM_KEYS` 取 `['color','body']`，样本来自 `item_feedback`（因变量默认 `aesthetic_score`，`--target=fit` 换 `fit_score`）。现有三维路径与 `MIN_SAMPLES=30` 一个字不改：那条门不是被废掉，是**留给"规则卡也有身体维"那天**（那是出路 A，见 §八）。
2. `MIN_SAMPLES` 二维档另定 **15**（C 档手拍值）。理由如实写：三维档 30 是"三个自由度各要 10 条"的量级感觉，二维同比例缩；这一句**不是文献结论， papers 目录里没有协同过滤/排序学习的原文**，所以对外 ⛔ 不许说"科学采样量"，只能说"够 15 条才开始给权重建议"。
3. 输出必须自带一句限定：**这是在 `{color, body}` 这个二维子单纯形上拟合的，不能拿来定 `rule` 的权重**，也不与第四阶段那组 `{0.1, 0.45, 0.45}` 直接比较。
4. 剔除原因逐条打点（沿用 `dropped` 那三个字段的写法，新增 `wrong_source`），⛔ 缺测不许当 0 分喂进去（硬规矩 2；`regress-rank-weights.js:84-93` 那段注释就是这一条的落地，二维档同样遵守）。

## 四、协同过滤层（`services/collabFilter.js`，本阶段的新算法层）

一句话定义：**"和你体型相近的人，在这个场合给这件衣服打了几分"**——它是一层**乘子**，不是第四个权重。

### 4.1 输入

- **分组键（cohort）**：当前人的体型向量＝`身高`、`净胸围`、`净肩宽`（实测优先，缺格由第五阶段 `bodyDimEstimator` 补、并带 `estimated:true` 标记）＋ 本次 `occasion`。⛔ 身高都没有 ⇒ 不组 cohort，整层隐身（`factor` 恰好 1）。
- **信号（likes）**：`item_feedback` 里同 cohort 其他 `actor_key` 给同一件 `wardrobe_item_id` 的星级。日记（`wardrobe_outfits`）**不作首选信号**——它一条是"整套搭配"的分，摊到每件衣服是均分假设（`16` §五 已经为同类问题写明：一条搭配里的衣服不是各自的样本）。

### 4.2 相似度与打分

- 体型距离＝三项标准化差绝对值的和；⛔ 不用皮尔逊相关（样本量撑不起，§〇 只有 5 个有衣柜的人）。
- 阈值与降权手拍（**C 档**）：距离 `≤ 0.35` 算同组、`K_PRIOR = 5`（经验贝叶斯收缩，`score = (n·均值 + K·全局均值)/(n + K)`）。
- 乘子 `factor = clamp(1 + 0.06 · (收缩分 − 全局均值)/4, 0.95, 1.05)`：⛔ 与偏好乘子同界（`16` §五 的 `[0.95,1.05]`），一组数字少一个真相源。
- 出账三件套：`cohort_size`（组内几人）、`n`（几条打分）、`basis`（人话一句）。**`cohort_size < 3` ⇒ 不出话术、`factor=1`**（隐私与噪声同一道闸）。

### 4.3 冷启动与反馈回路（`16` §六 欠的两条，这里必须还）

1. 冷启动：库里 `item_feedback` 0 行 ⇒ 这一层今天上线就是 100% 隐身。⛔ 不许为了让它"看起来在工作"而拿规则命中数或日记数冒充 likes。
2. 退出机制（自我强化）：本层 ⛔ **不进 `rankDims` 的三维出账**、不改 `algo_score_of`、不进回归自变量，只在总分末尾乘一刀；且 `provenance` 必须写明"协同过滤 ×1.0x"，报告里看得见，就能一键关（`enabled:false` 即完全透明，Top 8 逐条与改前相同——这条要有测试钉住）。

### 4.4 隐私口径（对外话术红线）

- ✅ "和你体型相近的人，在这个场合常给这件高分（同组 5 人）"。
- ⛔ 不许出现任何能反推到个人的组合：单条打分人、姓名、门店、时间戳一律不出前端；`basis` 里只允许人数与均值。
- ⛔ 在 `cohort_size ≥ 3` 之前，这一句整体不许出现在顾客端文案里（不是"改成模糊说法"，是不显示）。

## 五、门店模式接线（不做迁移就能修的那两条，B 出路的必经路）

1. `recommendEngine.js:1101` 的门槛从 `mode === 'personal'` 改成**"profile 里带了 `wardrobe_items` 就进"**（两档都开门）。门店场景里这些行只可能是**这次会话自己扫码录的那几件**，所以放开门也不会把 A 店的衣服推给 B 店的顾客——前提在第 2 条。

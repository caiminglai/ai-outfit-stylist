## 一、这一层的边界（先说清它不干什么）

1. **版型轴只回答"这件衣服对这个人的净围度差多少"**，不回答"好不好看"。松量—外观的证据只有 Liu/Fan/Lau 2006（9 名中国男性、白 T）与 Sakata 2020（20 名日本女性、衬衫），都低于 ITU-T P.910 的 ≥24 被试线 ⇒ 区间只能当先验（`docs/依据/08` §10.1、`docs/依据/09:210`）。
2. **本项目没有、因此这一层永远不判的东西**（写出来是为了不许当成漏实现）：袖长、袖笼弧长、领围、成衣实际尺码、面料弹性。`user_wardrobe` 只有 `shoulder_cm/bust_cm/length_cm/waistband_cm` 四格实测（`schema.sql:351-354`），没有 `fabric_stretch` ⇒ **负松量（紧身／压缩款）不建档**，见 §八。
3. **第 0 层与第 1 层的结论可以相反，不许调和**（`docs/依据/09:20`）。本轮不改动这条。

## 二、分层：一条松量轴 + 一条风格标签轴

### 2.1 松量轴（进分）

四个**数值档**是算式真正吃的东西，`FIT_TYPE_VALUES` 一个字不改：

| 规范值 | 放松量区间（cm） | 进算式的值 | 依据档位 |
|---|---|---|---|
| 修身 | 0~2 | 中值 1.0 | C 档手拍（无实证） |
| 合身 | 2~7 | 中值 4.5 | B− 档量级同源（Sakata 2020 女装衬衫合适松量 1~7 cm，n=20，【二手·摘要级】`08:255`） |
| 宽松 | 8~15 | 中值 11.5 | C 档手拍 |
| 廓形 | 15~26 | 中值 20.5 | C 档手拍；上端锚只作量级对照——GB/T 2668-2017 的 +20/+22/+26 是**成品设计实例、不是合体窗口**（`docs/依据/09:133` 已裁"不许拿它当窗口用"），故**不许引它背书 15~26** |

**为什么不给 oversize 们新立第五档、第六档**：新立一档＝新写一批没有依据的数，而且立刻要在"男友风比 oversize 少几 cm"这种没人测过的地方编数。现有四档的区间已经被测试和话术钉住（`test/topFitBody.test.js`），把新词归到档上，改动面只有一张别名表。⇒ **档不动，词扩。**

### 2.2 风格标签轴（不进分）

`甜美／优雅／简约／商务／休闲／时尚／通勤／复古／运动／学院／法式`（裸词）这类词**承诺的是搭配语境与轮廓气质，不承诺胸围放松量**——一件"法式"可以是收腰合身，也可以是宽松落肩。所以它们**不进 `fit_type`、不进任何算式**，只进 `user_wardrobe.style_tags`（`schema.sql:362`，JSON 数组列，展示与统计用；商品侧那两处 `style_tags` 用法是 `wardrobe.js:196` 的统计和 `:316` 的"标签丰富 +10 分"，本轮不动、也不许扩成版型判据）。

⚠️ 这一条与用户第六／七阶段那句"男性推荐简约/商务/休闲、女性推荐甜美/优雅/时尚"直接相关：**那些词属于这一轴，不属于松量轴**。把它们塞进 `fit_type` 会让"选了商务"这件事改变松量估计＝伪量化回归。

### 2.3 三档之间的边界：`男友风`、`法式慵懒`、`oversize` 为什么是"带松量含义的复合词"

它们各带一半松量承诺、各带一半风格承诺。本规范的切法：**松量那半进别名表，风格那半留在标签轴**（同一个词允许在两处出现，语义分工不同）。程度分配是 C 档手拍，写死在表里、可一行改判：

- `oversize`／`oversized`／`欧版`／`大版`／`茧型`／`斗篷式`／`boxy` ⇒ **廓形**
- `男友风`／`法式慵懒`／`慵懒风`／`落肩`／`宽松版`／`直筒宽松` ⇒ **宽松**

手拍的唯一说理（不当依据用）：oversize 话术承诺"整件大一码以上"，男友风／法式慵懒承诺"肩线下落＋袖长＋衣身不收"，量级差一个档。**这个判断可以一行推翻**，已进 §七 待裁第 1 条。

## 三、归一：显式别名表，认表不认猜

### 3.1 新函数

```js
normalizeFitType(raw) → { value: '修身'|'合身'|'宽松'|'廓形'|null, via: 'exact'|'alias'|null, src: string|null }
```

- 只做三件事：`trim()`（含全角空格）→ 查 `FIT_TYPE_VALUES` 精确键 → 查 `FIT_TYPE_ALIASES` 精确键。
- **不做**：小写化以外的字面变形、剥"风/版/款/型"尾缀、句内扫描、相似度就近归档。`'超大版'`、`'oversize风一点'`、`'宽松点'` ⇒ 一律 `value: null`。
- ⛔ **版型侧永远不做自由文本抽取**。色彩侧这轮能抽（`colorMetrics.js:874` `extractColors`），是因为色有物性锚（HEX→CIELAB→ΔE），抽出来的词能落到可测的数上；版型词在文案里没有数可落，抽词＝回到第二阶段废掉的那套词典。`schema.sql:345-347` 那句"不再从 name/style_tags 里猜中文词"照旧有效。

### 3.2 与旧口径的关系（`topFitBody.js:206-208` 那三行注释必须改口）

旧注释反对的是"把自由词**猜**成某一档"。别名表不是猜：表里每个词都是我显式写下的、可点名、可一行撤销的映射。**代码注释要按这个口径重写**，否则后来人读到旧注释会以为别名表违反规范。重写要点：

1. 保留"不做就近归档"这条禁令（针对算法），
2. 新增"认表不认猜：表内词有档，表外词回 `null`"，
3. 指明"每个别名进表要在 §2.3 式说理，说不清就不许进"。

### 3.3 缺测不出分（硬规矩 2 的同一句）

`value === null` ⇒ `topFitBody.js:581` 那一支不进、`ease_src` 保持 `null`、`missing.push('ease')` ⇒ 这一维缺席，不猜、不给默认档。表外词的原文原样进 `signals` 审计串（现在 `:556` 已在做，改的只是"值域"提示语要带上"可用同义词"）。

## 四、输入输出契约（改完之后必须成立的断言）

1. **写入口只存规范值**：`wardrobe.js:513`（INSERT）与 `:692-694`（PUT）先过 `normalizeFitType` 再进 `sanitizeEnum` ⇒ 库里 `fit_type` 的取值集合仍是那 4 个词，**零迁移、零 CHECK 变更、无需 DB migration**。
2. **审计留原词**：命中 `via === 'alias'` 时，`signals` 里必须出现「你选的『oversize』按版型档『廓形』估松量 = 区间 15~26cm 的中值 20.5cm」这类整句，出处可追到表。
3. **算式只认档、不认词**：`FIT_TYPE_EASE` 的键永远是规范值；别名表在算式的上游，不在算式里。
4. **同一件衣服，改前改后差分可复算**：`fit_type` 全 NULL 的现状（6/6）⇒ 本轮改动对**现有数据的输出分零影响**，唯一的可测变化是"新录入时能选新词"。这条是本轮最重要的安全垫，必须在报告里写明。
5. **`recommendEngine.js:1117-1121` 的 `hasFitType` 闸门**：改成"归一后有档才算在场"，否则用户选了 `oversize` 会一路走到 wardrobe 存成规范值、却在重排侧被认成缺席。
6. **前端类型**：`app/src/types/index.ts:594` 那个硬编码联合类型是本轮唯一的"前端会红"的点——表单若允许别名，类型必须放宽成 `string`，或把联合扩到全词表。**取前者**（后端已保证入库只有 4 值，前端提交的可能是别名原文）：`:594` 改为注释说明"提交值可为别名表内任意词形，服务端归一后落库只存规范值"，类型放宽。
7. **测试**：`test/topFitBody.test.js` 新增一块别名归一回归（每条别名逐个断言落到哪个档、表外词逐个断言回 `null`）；路由侧现有钉子必须同步改口——`test/auditFixes20261013.test.js:288` 那块「四档落库、认不到的值 400、PUT 传 null 清空」里 `:307` 用正则钉死了错误文案 `/fit_type 只能是 修身\/合身\/宽松\/廓形/`，`:304` 还拿 `'紧身'` 当"认不到的值"。⇒ 改 `enumError` 文案就必须同轮换这条断言；⚠️ **`紧身` 这一行不许改成通过**：按 §八 第 1 条它仍然要 400，它正好是新口径的天然负向样本。另补一条"传 `oversize` 不被 400 拒、落库是 `廓形`"。

## 六、依据档位与对外措辞红线

**能说的**：版型档 → 放松量区间是"把用户选的档换算成一个可比的数"；四档里只有"合身 2~7"与 Sakata 2020 的实测区间同量级；oversize／男友风／法式慵懒 归到哪一档是产品判断，一行可改。

**⛔ 不许说的**（对外文案一句都不许越）：

1. "国标规定了 oversize 的松量" —— GB/T 2668-2017 只给中山服/茄克的设计实例（+20/+22/+26），且 §3.3 自认"其他单服可参考实例设置" ⇒ 它**不给通用放松量**，T 恤/衬衫/连衣裙没有值（`docs/依据/01:110-111`、`09:133`）。
2. "我们科学量化了版型" —— 修身/宽松/廓形三档区间与全部别名映射是 **C 档手拍**。
3. "系统能看懂衣服描述里的版型词" —— §三 明写不做文本抽取。
4. "按国标判你该穿 oversize 还是合身" —— 国标管号型分档，不管款式偏好（`docs/依据/02:135-136`、`08:287`：ISO 8559-2 明说号型体系基于 body measurements、allowances 归厂商）。

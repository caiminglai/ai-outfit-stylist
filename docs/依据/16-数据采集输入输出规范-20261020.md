## 一、三个真卡点（本轮就修这三条）

### 1.1 卡点一：星级被二元按钮锁死

现状逐字：`ruleFeedback.js:15` 是 `const SIGNALS = ['useful', 'inaccurate']`；`recommend.js:155` 进门就 `if (!SIGNALS.includes(signal)) return 400`；前端 `RecommendationReport.tsx:177` 是 `if (signal) void submitFeedback(...)`——注释自己写着"已经表过态就立刻补一次提交，否则先记下、等点按钮时一起走"。

⇒ 用户只打星、不点👍/👎，**星永远停在浏览器内存里**。这不是没数据，是通路断在最后一步。

**修法（不建表、不加列）**：`SIGNALS` 加第三档 `'rated'`＝"只打了星、没表态"。

- `recountRules`（`ruleFeedback.js:78-84`）只按 `signal='useful'`／`'inaccurate'` 数好评差评 ⇒ 新档天然不进好评率，不需要改那条 SQL，但**必须补一条测试钉住它**，防止以后有人把 `'rated'` 也数进 `feedback_up`。
- `UNIQUE(user_id, group_id)`（`schema.sql:320`）不动 ⇒ 一人一规则只留最新一行：先打星（`rated`）、后点👍，同一行被覆盖成 `useful` 且星保留（靠既有的 `undefined＝这格不动／null＝明确清空` 契约，`ruleFeedback.js:88-92`）。
- 回归侧天然安全：`collectSamples` 的 binary 目标只认 `useful`/`inaccurate`（`regress-rank-weights.js:155`），`rated` 行走 `dropped.no_target`（`:161`）——不是 bug，是"没表态就不该当正负样本"。
- 前端：点星即提交；`api.ts:422` 的 `signal: 'useful' | 'inaccurate'` 放宽成三档。
- 措辞：`rated` 对人只写成"记下了你的星级"，**不许写成"你的评价已提交"**（用户会以为表过态）。

### 1.2 卡点二：日记后端半瘫 + 前端零入口

现量：`wardrobe_outfits` 有 11 列（`schema.sql:385-397`），但 `wardrobe.js:868` 的 INSERT 只写 `session_id, name, item_ids, occasion, season, notes` 六列 ⇒ `user_id`、`rating`、`is_favorite` **永远是 NULL**。路由只有 `GET /outfits`（`:794`）与 `POST /outfits`（`:820`）——**没有 PUT、没有 DELETE**，写进去就改不了也删不掉（删衣服时倒有一段连带清理 `item_ids` 的逻辑 `:759-771`）。前端：`grep -rn outfits app/src` 命中 **0 处** ⇒ 表 0 行是必然，不是偶然。

**修法**：① INSERT 补 `user_id`（走 `optionalUser(req)`，游客也有行）与 `rating`（1~5，复用 `scoreError` 那把尺子，越界 400）；② 新增 `PUT /outfits/:id`（改 `occasion/season/notes/rating/is_favorite`）与 `DELETE /outfits/:id`，两者都做归属校验（`session_id` 或 `user_id` 命中本人，认不到就 404，不许越权改别人的日记）；③ `OUTFIT_SCALARS`（`:105`）扩上新字段；④ 前端在衣橱页加一个"记一笔今天穿了什么"的入口：多选**已有单品**（复用现有衣柜列表）+ 场合（五个受控词下拉）+ 季节 + 审美/合身两把星。

🔴 **④ 的落地订正（10-20 当场）**：入口照做了，但**只有一格星**。`wardrobe_outfits` 在 schema 里只有 `rating` 一列（没有审美/合身两列），要两把星就得补列＝DB 迁移＝归你裁决（见 §七 第 7 条）。所以前端 `WardrobeDiary.tsx` 落的是"这套搭配整体几分"一个 1~5 星，`api.ts`/后端 PUT 也只认 `rating`。**推荐卡上那两把星（审美/合身）仍在 `feedback_events`，两处不是一个东西，别混着写。**

⛔ **本轮不加 `wear_date`、不加天气列**（那是迁移，归你裁决）。限制必须写死在文档与话术里：日记的"哪天穿的"只能退化成 `created_at` 的日期；天气不进日记（天气在推荐请求里已有通路：`recommend.js:182` 的 `data.weather` 与 `services/weatherService.js` 的 `buildTemperatureProfile`）。⇒ 所以本规范里的"根据天气学习"这一句**暂时不成立**，第八阶段第一步做不到，写清楚比含糊过去重要。

### 1.3 卡点三：星级进得了库，不一定进得了回归（齐率本轮未测）

`regress-rank-weights.js` 的自变量是 `rank_snapshot`，`collectSamples`（`:117` 起）要求 `rule/color/body` **三维都有 0~100 的分**，少任一维整条剔除（原因计数分 `no_snapshot`／`incomplete_dims`／`no_target`）。而 `rankDims`（`recommendEngine.js:681-687`）在色彩或廓形没出分时把那一维的 `score` 写成 `null`。

按本机体测底数（净胸围 3 人、肩宽 1 人、`bust_cm` 衣柜 0 行），大量真实反馈会被判 `incomplete_dims` 丢掉。**这一条本轮不修**（修法是改回归口径或让算法层多补维，都会动到第四阶段定下的权重逻辑），但要做两件事：① 采数前先测出"这个档案打一次星，快照三维齐不齐"，把齐率摆到报告里；② 偏好画像（§五）**不依赖三维快照**，走另一条独立的、样本少也能算的路。

## 三、反馈轴契约（改完必须成立的断言）

1. `POST /api/recommend/feedback` 的 `signal` ∈ `useful / inaccurate / rated`；缺 `signal` 仍 400；缺 `group_id` 仍 400。
2. 只送两把星 + `signal='rated'` ⇒ **库里落一行**，`aesthetic_score`/`fit_score` 有值，`feedback_up/feedback_down` 两个计数**不变**。
3. 星级越界（0／6／`'五星'`／NaN）仍 400 说破，不静默抹成"没打"（`ruleFeedback.js:39-50` 现口径不动）。
4. 游客可采：`optionalUser` 认不到登录态时按 session 造/取游客行（`middleware/auth.js:79-89`），**不新增强制注册**。
5. 一人一规则一行（`UNIQUE(user_id, group_id)`），重复提交覆盖，不累加好评数。
6. 前端点星即提交，未表态走 `'rated'`；`rank` 快照仍由前端把那张卡的 `item.rank` 原样带回（事后再查就是另一把尺子）。

## 四、日记轴契约

1. `POST /api/wardrobe/outfits`：必填 `name` + `item_ids`（数组、正整数、去重≤50 件、且都属于当前会话——这套校验 `:828-860` 现成，一条不许弱化）；`occasion` 只收 §〇 那五个受控词（表外词 400 并列出词表）；`rating`/`aesthetic` 类星级 1~5；`user_id` 从 `optionalUser` 取，**不信任前端传来的 user_id**。
2. `PUT /api/wardrobe/outfits/:id`：只允许本人改自己的行；字段级 `undefined＝不动／null＝清空` 与衣橱 PUT 同契约；越权 404，不返回 403 带信息（防枚举 ID）。
3. `DELETE /api/wardrobe/outfits/:id`：只删这一行，**不动衣物**（衣物被删时的连带清理已有 `:758-770`）。
4. `GET /api/wardrobe/outfits` 补 `user_id OR session_id` 两条口径取并集（历史行 `user_id` 为 NULL，只按 session 取会看见自己但看不见登录后的自己）——这条要在代码注释里写明为什么是并集。
5. ⛔ 不做"隐式合并同一天同一组合"：日记是用户写的，程序不猜哪两条是同一次。

## 五、画像轴：`backend/services/wearPreference.js`（本轮唯一新增算法层）

**输入**：`{ session_id, user_id }` + 现取的 `wardrobe_outfits`／`feedback_events`／`user_wardrobe` 三类行。
**输出**：`{ dims: [{key, value, samples, basis}], factor, provenance }`，每一维独立带 `samples`（样本数）与 `basis`（这几行算出来的，可打到报告里）。

维度（全部可解释、全部来自用户自己的记录）：

1. **色族偏爱**——把日记里那几件单品的 `color`/`color_tags` 喂第六阶段的 `colorMetrics.colorFamily`（`:784`），按"同一族被穿了几次"计数；⛔ 不新算任何色差。
2. **场合覆盖**——五个受控词各自的次数（`occasion`）。
3. **季节**——`season` 计数。
4. **版型档**——`user_wardrobe.fit_type` 落在 4 档的分布（第七阶段的别名表还没落地，本轮**只按现值域 修身/合身/宽松/廓形 计**，认不到就不计）。
5. **星级均值**——审美/合身分别取均值，与样本数一起出。

**闸门（这是这一层的命门）**：

- `MIN_SAMPLES = 3`（**C 档手拍**，先拍严）：某一维样本 <3 ⇒ 该维**缺席**，不出分、不参与乘子。这就是硬规矩 2「缺测不出分」在采数层的落地。
- `factor ∈ [0.95, 1.05]`（**C 档手拍**，乘性、有界）：只给"你自己常穿的那一族/那一档"一点顺位加成，幅度小到不可能盖掉色彩与廓形两维的真分。⛔ 不改第四阶段定的三路权重（0.1/0.45/0.45），⛔ 不做加法（加法会跟 0~100 的分搅在一块儿，且没法解释）。
- **零样本零影响**：没有日记、没有星 ⇒ `factor` 恒为 1，且必须实测"改前改后 Top 8 逐条相同"。这条是本轮唯一能自证安全的断言，要写进测试。
- 接法：`rankDims` 出总分后乘这一维（与 `factor`／`algo_penalty` 同层出账，审计串里能拆账），出账字段带 `preference_basis`。

⛔ 措辞红线：这一层**不许叫"机器学习""AI 学会了你"**。对外只能说"按你自己记下的搭配，把常穿的色系和场合稍微排前一点"。样本阈值 3、幅度 0.95~1.05 全是我手拍的，属于 C 档，不许称"量化/科学"。

## 六、协同过滤（第二步）——本轮只立边界，不写一行码

你说的原话是"当用户量达到一定规模时"。现量给出"规模现在在哪"：`body_metrics` 14 行、净胸围 3 人、肩宽 1 人、日记 0 行、反馈 0 行。

⇒ **今天算不出"和你体型相似的用户"**：可比体型向量只有 12 个人有身高、6 个人有身高+体重，肩宽 1 人。三条前置必须先满足（写进路线，不许跳过）：① 第一步的采数通路真的跑起来、② 档案侧体测字段的填写率上来（第五阶段的估算只能补净胸围/肩宽，补不了用户没填的身高体重）、③ 定一个最小样本阈值与冷启动回退（不足则退回现有规则+算法重排，不冒充个性化）。

另外两条必须在这一层定死，不能等写码时再想：**跨用户可见性的隐私口径**（"相似用户都喜欢穿"这句是把别人的行为暴露给你，要匿名化到不能反推个人，且要合规）与**反馈回路**（推荐出去又被点星，会自我强化，得有退出机制）。

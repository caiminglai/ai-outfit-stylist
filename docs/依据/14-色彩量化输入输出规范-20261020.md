### 1.4 授权红线（第四阶段就写了，本轮再钉一遍）

色名→HEX 整表**必须我们自建**。单个颜色名和它的大致色相是常识，但**一本书或一家色卡整理出的整套"名字＋数值"是受保护的汇编与授权资产**（Pantone 还牵涉商标与订阅条款）。抄《中国传统色彩名录》或任何色卡整表＝不可用资产进可用代码。表建好之后，每个键在依据台账里按 C 档登记，来源栏写"本工程标定"。

### L3 `COLOR_SYNONYMS`（口语同义，**只并在同一明度族内的写法**）✅ `:423`，现量 42 条别名

- 允许：`卡其 → 驼`？⛔ 不许（现量：卡其现在压根不在表内，补进来时按它自己的自建 hex 走，见 §七 待裁 1）。允许的形如 `雾霾蓝 ↔ 霾蓝`、`藏青 ↔ 藏蓝`、`榄绿 ↔ 橄榄绿`、`鹅黄(色) ↔ 鹅黄`——**两侧 ΔE00 必须 < 5**（同一口语叫法、同一撮色）才算同义，这条阈值本身是 C 档。
- 🔴 **明确禁止**：`驼色 = 卡其色 = 棕色` 这种合并。现量 `deltaE00(驼色, 棕色) = 25.4`（L 分别 62.3 与 37.8，一中明度一低明度），25.4 正落在 `FUSION_GATE` 的 15~30 触发带里 ⇒ 合并＝把"该触发同色糊合闸门"的一对判成同一个色，抹掉一整类真实结论。**这三者的共同点不是"同一个色"，是"同一个色系"** ⇒ 系归属进 L4，不进 L3。

🔴 **落地时的两步偏差**：① **"两侧 ΔE00 必须 < 5"这条判据本身立不住**——别名一侧根本没有 hex（有 hex 就该直接进 L1），拿什么算 ΔE00？所以建成的是一条**反向**断言：把禁止合并的对逐条写进 `COLOR_ANTI_SYNONYMS`（`:475`，7 组，每 pair 的 ΔE00/L/C 都是现量），断言"非 `same` 的每对必须两个 hex 不相等 **且 ΔE00 ≥ 4**"（4 不是 5：这批里最小的是 珊瑚粉↔珊瑚橘 4.1，取 5 会让测试当场红）。② 规范举的四个"允许的形如"有半数没进表——`鹅黄(色)↔鹅黄`、`雾霾蓝↔霾蓝` 这类**靠"去尾／补尾『色』"两步机械规则自己就通了**，写进同义词库是死代码；实测撞键的 拿铁/摩卡/抹茶/米色/苹果绿 本来就已经是 L1 的键。于是这张表只收**字面不同**的（咖啡色↔咖啡棕、松石绿↔绿松石、裸色↔奶杏色），并做成三条可计算不变量：别名不撞键／指向的规范键必须在表内且能出 Lab／走机械规则时必须**认不出**（认不出才证明这条同义词不是死代码）。现量 42 条，三条全过（判据＝工装 `phase6-20261020/synonym-check.cjs`）。③ 那对禁并的数还补了一条：驼↔卡其 **6.8**、卡其↔棕 **28.6**，L 分别 62.3／63.1／37.8——所以 §七 待裁 1 的"卡其自己建一格"已经按现量落定。

### L4 `COLOR_FAMILY`（色系软标签，不参与色差计算）✅ 落成三张表一张函数：`COLOR_FAMILY_WORDS` 43 词 `:526`／`COLOR_FAMILY_OVERRIDES` 9 键 `:583`／`COLOR_HSL_FAMILY_BANDS` 8 段 `:598`／`colorFamily()` `:784`

🔴 **落地时改了族集合，也改了判据**：① 族**不是**规范里那六个（大地色/莫兰迪/低饱和/暖调/冷调/中性），而是十个**看得见的颜色族**——红/橙/黄/绿/青/蓝/紫/粉/棕/无彩色。理由是拿两把尺子比过 232 键全表（工装 `phase6-20261020/family-ruler.cjs`）：按 **Lab 色相角**切段与色名自带族字打架 **106/221** 条（驼色 h78、鹅黄 h93、黄 h92 全落进"绿"区——低彩度暖色上 Lab 的角根本不分黄/绿/棕），按 **HSL 角**切打架 **61/221** 条，所以主判据取**色名里位置最靠后的那个族字**（灰紫⇒紫、蓝灰⇒灰、藕粉⇒粉），名字里没族字的（藏青／焦糖／拿铁／莫兰迪…）才退回 HSL 角，退回还判错的 9 个键走覆写表点名（卡其 46° 会被算成黄 ⇒ 判棕、勃艮第 340° 算成粉 ⇒ 判红）。② 消费面比规范窄：这一层现在**只出标签，没接"上下同色系"判**——`colorFamily` 的产物只落在两处（`extractColors` 每段的 `family` 字段、`color_fit.family` 随 API 给前端），排序层一个数没吃它（"绝不进 ΔE00、绝不进三轴权重"这条守住了，代价是 §五 ④ 那句"同色系判"没做，登记在 §9.4 第 2 项；原先那句"见 §九 偏差 5"同样是悬空指针）。

`大地色 / 莫兰迪 / 低饱和 / 暖调 / 冷调 / 中性`。用途只有两个：① 判"上下同色系"这类搭配语；② 给报告一句话解释。**⛔ 绝不参与 ΔE00、绝不进三轴权重**。语料里"同色系"9 次、"大地色"6 次、"莫兰迪"5 次，就是这层要接的东西。

### L5 `LIGHTNESS_BANDS`（明度族，这一层才是"深色系"的正解）✅ `:622`（三档）＋ `LIGHTNESS_TOKENS` 14 个词形 `:629` ＋ 出分分支 `_bandOnlyFit` `:1070`

🔴 **落地时的三处加码**：① 规范只列了深/浅两档，实际建了**三档**（深 `lMax:35`／中 `lMin:35,lMax:65`／浅 `lMin:65`），"中间色／中性色"这两个词形在语料里确实出现，不给档就只能丢弃或误并进浅档。② 明度轴**不是**"按区间中值算"，而是每档带一个手拍的 `brightenHint`（深 0.8／中 0.5／浅 0.2）直接喂 `brighten` 轴——比中值诚实，因为它承认"这里没有 Lab、只有方向"；色相与彩度两轴各按无信息记 **0.5**（与无彩色同一写法），`deltaE00／dHue／dL／chroma／top_hex` 全为 `null`、`fusion_gate` 钉 1（没有两个 Lab 可差）。③ 每个档位提示值与切点都写进返回值的 `evidence` 里，明写"本工程 C 档手拍，不是文献值"，`basis: 'lightness-band'` 一路带到报告与后台。⚠️ 已知的外观缺口：只命中明度档时 `top_label` 打出来是「中间色」这种档名而不是颜色名，报告行读起来像"推了一个叫中间色的颜色"——纯措辞问题，不影响分数，挂在 §七 待裁旁边等一起定。

| 输入词形 | 出参 | 参与哪一轴 |
|---|---|---|
| 深色／深色系／墨／暗 | `{ L_max: 35 }` | 只进 `brighten`（衣装越暗⇒脸被评为越显白，Zhang 2025，B 档） |
| 浅色／浅色系／亮／淡 | `{ L_min: 65 }` | 同上 |
| 中性色 | `{ family: '中性' }` | 进 L4，不进明度 |

- ⛔ **这一层没有 hex**。`colorFit` 收到只有明度族的信息时，走的是"色相轴按缺测记账（`hueContrast` 钉 0.5、`hue_applies:false`）＋明度轴按区间中值算"这条新分支，跟现在无彩色那条分支同构，账目里必须写明 `basis: 'lightness_band'`，让任何一条推荐都能拆回是"实测色"还是"明度族"给的。
- 为什么不直接编一个深色 hex：那等于给 226 次"深/浅/亮"发一张假色卡，ΔE00、色相角、彩度全跟着假，而且它占总分 45%＋20%。
- "深色系显瘦／提升气场"（你第六阶段指令里给男性的那条）**本机没有可引的原文**：`10` 那两篇赫尔姆霍兹条纹论文证的是横条纹，不是"深色显瘦"。⇒ 这条只能作为产品取向（C 档）写进规则文案，不许写成量化结论，见 §七 待裁 2。

## 三、函数契约（新写的三个＋改链的一个）

```js
// 1) 归一
normalizeColorName(input) -> { name, hex, via } | null
//    via ∈ 'exact' | 'strip-suffix' | 'bare-word' | 'synonym'；查不到返回 null，不猜

// 2) 抽色（你要的"驼色大衣→驼色"在这层）
extractColors(text, opts?) -> [ { segment, name, hex, lab, family, band, is_specific } ]
//    · 先按分隔符切片：+ ＋ 、 ， , / 空格 或（1.2 现量：color_combo 里 + 105 次、空格 90、/ 58）
//    · 每个片段取该片段内**最先出现**的色词（沿用 _firstColorNameIn 的"句内位置"口径，不是表内顺序）
//    · 一个片段里两个具名色（"雾霾蓝灰"）⇒ 取归一链第一个，并把第二个记进 `also`
//    · 只命中明度族 ⇒ is_specific:false、hex 为 null、band 有值（不许把 band 伪装成 hex）
//    · 全片都认不出 ⇒ 返回 []（空数组＝没信息，调用方按缺测办；不是 null 也不是 0 分）

// 3) 明度族
lightnessBand(text) -> { band, L_target } | null

// 4) 改链：resolveColor(input)
//    新顺序：hex → 精确名 → normalizeColorName（含剥尾缀/裸字/同义词）→ 句内子串 → 明度族（只回 band，不回 hex）
//    ⛔ 现在 `:240` 那行 ownValue 原型链守卫不能退化（键名写成 'constructor' 会拿到 Object 构造器，
//    一路当成"颜色"传下去，最后 hexToLab 认不出、分数无声消失）——扩表以后这条测试必须还在。
```

`colorFit` 的签名**不加新必填参数**（现量：生产代码里 4 处调用——`recommendEngine.js:995`／`:1002`／`:1059` ＋ `topFromBody.js` 1 处；`resolveColor` 在 `colorMetrics.js` 之外只有 `topFitBody.js:648` 一处在调），新增的是可选第三入参里的 `band`，并在返回值里多 `basis`（`'named-color' | 'lightness-band' | 'measured-hex'`）、`synonym_via`、`family` 三个审计字段。

🔴 **10-20 落地后的对照**（这四处是"规范说什么／代码成了什么"的账，逐条展开在 §九）：`normalizeColorName` 返回的是**规范键字符串或 `null`**，不是规范里那个 `{name, hex, via}` 对象——`via`/`basis` 挪到内部统一入口 `_resolveDetailed()`（`:718`）上出，`resolveColor()`（`:754`）仍然只回 hex，**老 4 处调用一行没改签名**（这是刻意的：改签名要动 4 个消费点＋它们的测试，本轮目标是认色不是重构）；`basis` 取值也不是那三个，是 `hex`／`table-key`／`strip-color`／`add-color`／`synonym`／`in-text`／`lab-object`／`lightness-band` 八个，粒度对准"第几步认出来的"。`extractColors` 的返回段字段是 `{text,label,hex,lab,family,band,is_specific,basis,via}`（规范写的 `segment` 实名 `text`）。`lightnessBand(input)`（`:858`）按规范存在。调用点现号：`recommendEngine.js:1037`（规则链）／`:1051`（衣橱链）／`:1118`（候选批量）＋ `topFromBody.js:393`；`resolveColor` 仓外一处 `topFitBody.js:653`。`ownValue` 原型链守卫（规范里那条 ⛔）现在在 `:732`；⚠️ **但那条负例测试在本文件建档时并不存在**（规范写的是"扩表以后这条测试必须还在"，`git show HEAD:backend/test/colorMetrics.test.js` 里 `constructor` 命中 0 条——写规范的时候就把"应该有"当成了"已经有"）。10-20 当场补上：`test/colorMetrics.test.js` 新增「原型链守卫：词表扩到 232 键后 constructor/__proto__ 这类键名仍取不到原型上的东西」，5 个原型键名 × 三个入口（`resolveColor`／`normalizeColorName`／`colorFit`）都必须是 `null`，并且"垃圾键混在正常色里"那段仍要认出 `藏蓝`（防守卫把输入一起判死）。该文件测试块 19（HEAD）⇒**28**（现役），全绿。

## 一、这一阶段做什么、不做什么

做两件（都在第一步里，顺序固定）：

1. **肤色采集**：表单里加"拍张照取色"。浏览器本地把照片画进 canvas，默认框取脸颊候选块（可拖动微调），取该块 **RGB 中位数**（⛔ 不是均值：均值会被一根发丝/一块阴影直接拖走）→ sRGB→Lab（A 档换算，与后端同一条）→ **只用色相角 h° 判冷暖轴**（冷皮／自然／暖皮）→ 用户**点一下确认**才写进 `profile.skin_tone`，并随请求体带一个 `skin_hue`（那个色相角）供量化层合成。照片**不上传、不落盘、不进库**。
2. **色彩量化**：把喂给 `colorFit` 的肤色从"8 个离散锚点"升成**连续 Lab**——`L` 与 `C` 取自用户确认的深浅档锚点（人照镜子选的那一格，比照片可信），`h` 取自照片采样，**由后端合成** `{L,a,b}` 直送 `colorFit`（⛔ 前端不送 Lab，见 §2.4 那条）；四处取值点收成一个带 provenance 的 helper。**三轴公式、`WEIGHTS`、`FUSION_GATE`、第四阶段权重一个数都不动。**

⛔ 不做（写死，别在路上捡）：不做人脸检测／关键点定位（要新依赖或要模型文件，两头都归你点头）；不写 `face_features`（那张表 0 行且有 `photo_id NOT NULL` 外键，取色不上传就没有 `photo_id` 可填）；不算也不展示 ITA°（`itaClass` 保持零调用）；不接 DashScope 视觉（要 key＝要花钱，且它现在失败退随机＝正面撞硬规矩 2）；不做 DB 迁移（`face_profiles` 存不下"这格是拍照来的还是手选的"，这笔欠账挂 §七 第 1 条）；不改配饰/妆容那两条 `includes()` 消费路（`:155-156`/`:275-276`）。

### 2.2 冷暖轴判据（后端唯一口径，`colorMetrics.js` 新增 `skinUndertoneFromHue(hue)` 与常数表 `SKIN_HUE`）

切点取 **华裔全部 h° 的 P25＝52.86 与 P75＝64.02**（B 档人群分位），**切法本身是 C 档**（人群分布只给位置，不给判据）：

```
h ≤ 52.86 ⇒ '冷皮'      h ≥ 64.02 ⇒ '暖皮'      之间 ⇒ '自然'      lab 缺/非有限 ⇒ null
```

现量自洽（工装 `cut-selfcheck.cjs`，8 个锚点各按自己的 h° 过这条线）：`冷皮 49.76→冷皮`；`白皙 60.26／自然白 62.10／自然 62.24→自然`；`暖皮 67.75／偏黄 74.36／小麦色 71.57／古铜色 72.35→暖皮`。⇒ 三档人数 **1／3／4**，方向与锚点表自带的语义一致（a\* 高的落冷、b\* 高的落暖）。⚠️ 同一次运行也量出**绝对明度为什么不能用**：`#E8C4B8` 这块典型"亮皮肤" sRGB 经 `hexToLab` 得 **L=81.89**，比华裔 P95＝65.87 还高 **16 个点**——照片/显示器的皮肤色本来就不在测色仪的人群分布里，所以深浅那一轴**只能人选**。

### 2.3 深浅轴（不自动写）

`skin_tone_detail` 保持用户手选；UI 在取色后**只提示一句**"深浅请照镜子确认（照片判不了明暗）"。⛔ 禁止用 L 分位替用户选深浅。

### 2.4 写入与出参

- 前端确认按钮是唯一写入口：确认后把档名写进表单既有格子（`skin_tone`），⛔ 不改 `CustomerForm`/`PersonalProfileForm` 的手选按钮语义（手选照常能覆盖）。
- 请求体新增一格 `skin_hue`＝**一个数**（采样色相角，单位度）；可选再带 `skin_hex`（`#rrggbb`，只为拆账与复现，⛔ 参与不了计算）。🔴 **本规范没有 `skin_lab` 这一格**：客户端递不进连续 Lab，明度与彩度只能来自后端那张锚点表——否则任何人能把 `L=95` 塞进引擎，而 §2.2 末尾那条反例已经量明"照片里的绝对明度不是肤色"。
- 后端 `routes/recommend.js` 的 profile 形状校验**不收紧**（`typeof profile === 'object'` 那条照旧），`skin_hue` 的合法性由 §2.5 的 helper 判，不在路由层抄第二份尺子。
- 响应里新增三格拆账：`_computed.skin_source` ∈ `photo_sample`（这次角度真的接管了色彩维）／`manual`（只有档名）／`archive`（沿用库里的档案）／`null`（肤色整格空着 ⇒ 色彩维必然缺席）；`_computed.skin_hue`＝后端认下的那个角度；`_computed.skin_undertone`＝后端按 §2.2 切点**对同一个角度现算的档名**。⛔ 这三格只拆账，⛔ 不是置信度，⛔ 不进任何公式。

### 2.5 量化层取值（`recommendEngine.js` 收成一处）

新增模块内 helper（名字与落点写死，便于测试按名点它）：

```
_skinForColor(enriched, profile)
  depthLab = skinToneToLab(enriched.skin_tone_detail || enriched.skin_tone || profile.skin_tone)
  hue = Number(profile.skin_hue !== undefined ? profile.skin_hue : enriched.skin_hue)
  ① hue 有限 且 hue ∈ [36.36, 78.05]（§2.1 那道 h 闸）且 depthLab 拿得到
       ⇒ { L: depthLab.L, a: depthLab.C·cos(hue·π/180), b: depthLab.C·sin(hue·π/180) }，source='photo_sample'
  ② 否则原样返回 depthLab（可能是 null），source 按它来自请求体还是档案记 'manual' / 'archive'
  ③ depthLab 与 hue 都没有 ⇒ null（colorFit 收到 null 照旧回 null＝缺测不出分）
```

四处调用点（`:1047`/`:1072`/`:1096`/`:1128`）全换成它，⛔ 不许留下第五处自己拼字符串。

🔴 配套一条写死：**深浅档拿不到时照片那一维不接管**（走第 ② 步，`source` 永远不等于 `photo_sample`）。理由＝合成 Lab 的 `L` 与 `C` 只能取自用户照镜子选的那格锚点，⛔ 不许拿人群 P50（L 58.58／C 20.61）去补一个"看起来像实测"的明度——那是硬规矩 2 逐字禁止的动作。⇒ **用户只确认冷暖、深浅留空时色彩维照样出分**（`冷皮`/`自然`/`暖皮` 三词本身就在 8 锚点里），只是不吃那个角度。

## 三、边界禁令（违反任何一条就是本轮的错）

1. ⛔ **默认肤色／随机值／"取不到就当自然"**＝直接违硬规矩 2。闸门不过必须明说取不到。
2. ⛔ **不得用照片值覆盖用户手选**：手选优先，照片只在"这一格本来是空的"时经用户确认填入。
3. ⛔ 照片字节**不得出设备**：不 `fetch`、不 base64 进请求体、不进 `localStorage`；canvas 用完置空引用。
4. ⛔ 不得写 `face_features`，不得新增 `photos` 行，不得动 `analysis.js:35` 那句 **501**（它现在的含义是"自动识别肤色**作为测量**尚未开放"，本链路给的是"候选＋确认"，不是那条被关掉的路）。
5. ⛔ 不得算/展示/入库 ITA°，不得引 `itaClass`。
6. ⛔ 不得改 `colorFit` 三轴公式、`WEIGHTS`、`ACHROMATIC_C`、`FUSION_GATE` 的任何数值（那是 `14` 的地盘，重切要先有反馈数据）。

## 二、解锁真相源：`backend/services/paidReport.js`（新文件，本轮唯一新后端模块）

**身份口径**：一律用 `users.id`（不是 `session_id`）。依据＝`middleware/auth.js:56` 的 `ensureGuestUser` 与 `:79` 的 `optionalUser`：只带 `X-Session-Id` 的游客也会被补一行 `users`，`loginRequired`（`:64`）之后 `req.user.id` 恒可用；`payment.js` 的四条写读口（`:130`/`:152`/`:252`/`:312`/`:356`）本来就全挂 `loginRequired`，所以**付了钱的人天然有 `users.id`**，权益跟着它走即可，⛔ 不再另造一个 key。

**发放数（granted）逐字定义**：

```
granted = COUNT(payment_orders WHERE user_id = ? AND status = 'paid')
        + COUNT(deposits     WHERE user_id = ? AND status = 'approved'
                           AND NOT (admin_note LIKE '微信在线支付 %'
                                 OR admin_note LIKE '支付宝在线支付 %')
                           )
```

- 第二项就是 §〇 第 3 条那把 `isOnlinePaid` 尺子的"非镜像"侧。⛔ 用 `proof_url <> ''` 当第二判据：**不行**——人工凭证流的 `proof_url` 是必填、在线镜像那几行写死 `''`（`:122`），所以拿 `admin_note` 前缀为主判据、`proof_url` 只当辅助；实现里两条都验，与 `payment.js:443-446` 完全同式。
- `amount` 是 REAL（`deposits` 那列），`amount_fen` 是 INTEGER（`payment_orders` 那列）。⛔ 相加前先各自取整到分：凭证那一路用 `Math.round(amount * 100)`。汇总只出"笔数"和"元"，⛔ 不在服务层用浮点做累加。

**已领数（used）**＝`COUNT(recommendation_logs WHERE user_id = ? AND json_extract(result, '$.paid_report.out_trade_no') IS NOT NULL)`。

**硬约束是"一单一报"，不是额度计数器**：领取按 `out_trade_no` 定位，判据＝

```
SELECT id FROM recommendation_logs
 WHERE user_id = ? AND json_extract(result, '$.paid_report.out_trade_no') = ?
```

命中就返回那一行（⛔ 不重算、⛔ 不新增）；没命中才生成。⇒ 同一单点一百次领到的是同一份报告（可重复查看是 receipt 的基本权利），付两单则能领两份。**额度读数只用于显示"还能领几份"，⛔ 不参与判定**，这样即使两张账口径将来有偏差也不会把人锁在门外。

**⛔ 不许出现的三种写法**：不许把权益存成 `app_settings` 里的一个数（那是可被改价页顺手覆盖的位置）；不许为"领过没领过"新增列或新表（§一 已定，加列要库迁移＝归你点头）；不许用 `created_at` 当日志时间去推"这人付了多少钱"（`datetime('now')` 是 UTC，见 §七 第 4 条）。

### 12.2 规范自身写错／写漏之处（七条，全部改码或点验当场撞到的）

1. 🔴 **§二 那句「身份口径一律用 `users.id`」对门店链路不成立**——门店档写 `recommendation_logs` 时 `user_id` 恒 NULL（`customer_sessions` 表没这列，`schema.sql:269-278`），归属只有 `sess_…` 会话号。后果现量＝**付了款的门店顾客领取时一律撞 409**（真浏览器点出来的，不是推的）。§〇 第 6 条只验了"带身份的推荐"那条日志，没验门店日志的归属列，这是规范的漏检面。修法三层：`findBasis` 改成「本人 ∪ 本次会话号」并集（`paidReport.js:169`，⛔ 不放宽到全表）；路由接 `?session=`（`payment.js:483-484`，形状闸门逐字复用 `middleware/auth.js` 的 `optionalUser` 那把尺子，别的样子一律当"没带"）；前端在 `createCustomerSession` 成功时把会话号存进 `style_ai_customer_session`（`api.ts:344`/`:360`），领取时回指（`:1098`）。
2. 🔴 **§八 第 2 条「复用既有渲染器」漏了渲染器内部还有一道模式闸门**——`RecommendationReport.tsx` 原 `:338` 写死 `mode === 'personal' && analysis`，于是后端把 B 节整块算出来、付费屏仍然一个字节不出。这条**只有真浏览器能发现**：验收矩阵第 8 条验的是引擎返回体（`algorithm_analysis` 非 null），它对 DOM 不敏感。改判据＝`mode === 'personal' || Boolean(recommendation.paid_report)`（`:343`；`paid_report` 只有领取那一路会写），⛔ 免费屏没有这个键 ⇒ 复点确认命中 0，一个像素没变。
3. 🔴 **§八 第 1 条「沿用既有 `X-Session-Id` 送出路径」掩盖了付款页与展厅是两套游客键**——`pay.html` 原来自己造 `style_ai_guest`，展厅用 `style_ai_session`／`style_ai_account`，同一个人两张 `users` 行：订单挂在 A 行、输入快照挂在 B 行 ⇒ 修完第 1 条还是 409。修法＝`ensureSession` 先复用展厅共享号、再退回自有兜底、最后才打 `/api/auth/guest`（`pay.html:131-147`），⛔ 本页不往共享键写（避免反过来污染展厅身份）。**规范该在 §二 就把"付款页与展厅必须是同一个 `users.id`"列为硬约束**，这条今天只落在注释里。

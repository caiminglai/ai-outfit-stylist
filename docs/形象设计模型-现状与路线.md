# 形象设计模型 —— 现状缺口与实施路线

> 定稿：2026-09-23。数据全部为本机实测（`backend-node/db/styleai.db`），**服务器那份未取证**。
> 本文是活文档：每落地一步，就把该步的"未做"改成"已做 + 实测数字"。

## 一、目标

把一个人身上的所有条件（肤色、身高体重、胸围、肩宽、腿长、脸型、眼型、鼻型、唇型、三庭五眼比例……）
数字化成一个**长期存在的"数字形象"**，再用一套科学 + 美学的计算，对这个形象给出穿衣搭配、妆容、
造型与配饰的完整设计建议；并随着样本积累到足够规模，用人群数据反哺每个人的推荐。

## 二、三层结构（合理）

| 层 | 存什么 | 现在的载体 |
| --- | --- | --- |
| 个体层 | 一个人的全部条件，长期不丢 | `body_metrics` / `face_features` / 三柜（衣橱·化妆品·配饰） |
| 样本层 | 每次「输入 + 输出 + 结果」各一条，攒成"一类人" | `recommendation_logs`（含 `input_snapshot`） |
| 计算层 | 规则 + 人群统计，产出建议并解释为什么 | `rule_groups` / `rule_conditions` / `profileEnricher` / `recommendEngine` |

三层的关系是单向依赖：**个体层不入库 → 样本层挂不到人 → 计算层永远只能拿到"这一次表单"**。
所以缺的不是算法，是"写入 + 归人 + 反馈"这三段管道。

## 四、当前断点（2026-09-23 实测）

原来量出的断点里，**不入库、不读档案、不挂人（个人侧）、标签留不住、无反馈** 这五条已经解决，第五节进度列带具体数字。

第六条「门店回头客没有身份」**2026-09-23 已定案关闭：门店不收手机号、也不收会员号**。门店继续只用那张 2 小时过期的临时会话表，同一个人第二次来就是一条新样本。

定案带来的三条后果，写在这里免得以后又被当成新 bug 翻出来：

1. 门店侧永久攒不下"可归属到某人"的样本，人群统计只能按条件切片、不能按人回溯。
2. 报告页的长期标签那一行门在个人模式（`serviceMode === 'personal'`）⇒ **门店屏幕上看不到形象标签**，这是设计不是回归。
3. 门店顾客想享受"第二次来不必重填"只有一条路：在个人模式注册账号。以后要改这个口径，需要他重新拍板。

「无反馈」这条已通：每条建议下面能点「有用 / 不准」，好评差评直接进规则分。只收这一个动作，**没有做「收藏」**（理由见第五节第 5 行）。

## 六、写规则时的科学与美学约定

- **先科学后美学**：任何一条美学规则都必须能被档案里的字段触发，不写"流行""高级"这类无主参照。
- **一条规则只解决一件事**，按四类各自成组：比例（60-30-10）、色彩（冷暖 / 金属色）、量感与线条（Kibbe 方向）、场合与着装规范。分组独立才谈得上以后按样本调权重。
- **每个输出必须带"为什么"**：现在 `algorithm_analysis` 已在前端渲染，不再新增只给结论、不给理由的规则。
- 条件字段与动作类型的中文名**单一来源**是 `services/ruleExplainer.js`（`FIELD_LABELS` / `ACTION_LABELS`）；后台下拉里那份（`static/admin/admin-utils.js`）是手抄的副本，新增字段两处一起登记、措辞一字一样。启动补齐种子时会按 `FIELD_LABELS` 校验，写了不认识的字段直接拒绝入库。
- **派生字段的取值不许在规则里另抄一份**：`color_season` / `color_season_12` / `kibbe_type` / `bmi_level` / `height_range` 这类是引擎算出来的，规则里写的值必须和 `services/profileEnricher.js` 导出的那张映射表一字一样——差一个字这条规则从写下起就永远命中不到，而且不会报错。种子测试直接从同一张导出表反查"每个取值至少被一条规则命中"，就是为了兜住这个。

## 七、工程与数据约束

- **档案是长期数据**：不设保留期、不做定期清理；只有顾客主动删除才删，且一次删干净——档案、标签、反馈、样本日志、搭配记录、照片与试穿结果连同 `/uploads` 里的文件全部连带清掉，不留"库里删了、文件还在"的尾巴。
- **`schema.sql` 不代表线上表结构**：它只写"新库怎么建"，`CREATE TABLE IF NOT EXISTS` 从不改动已存在的表，老库里同一张表的约束可能比它严（实测 `tryon_results.user_id` / `photo_id` 在线上是 NOT NULL，schema.sql 里写的可空）。判断某列能不能写 `NULL`、有没有默认值，只能对**正在用的库**跑 `PRAGMA table_info(表名)`；照 schema.sql 写插入语句会得到一条表面 200、日志里静默失败的假成功。
- 新增字段必须**同时**登记 `db/schema.sql` 与 `db/init.js` 的 `MISSING_COLUMNS`，否则服务器那份库不会自动加列。但**给新列建索引绝不能写进 `schema.sql`**：建表脚本跑在补列之前，老库上那句 `CREATE INDEX ... (新列)` 会让容器启动即 `no such column` 崩溃循环，索引必须放在补列循环之后。"启动日志看着正常"不算验收，还要再打一次库确认列真在。
- 建表类改动**不提交 `styleai.db`**（服务器启动期自建；提交了反而会被自己那份脏库挡住 pull）。
- **新增内置规则不写库、不改库**：写进 `db/seed/rules-*.json`，启动时按 `source_key` 只补缺（已存在的连优先级和开关都不动，后台改过的照旧生效）。`db/` 是整目录挂载，服务器只要 `git pull` + 重启容器就拿到新规则，不需要重建镜像。不用 `seed.js` 是因为它全删再全建：会把门店后台手工加过、关过的规则一起清掉，而且顾客点过一次反馈后 `rule_groups` 就有外键引用，整笔重建当场报外键约束失败——现在库里已有规则时它会直接拒绝执行（要真重建得显式加 `SEED_FORCE=1`）。
- 改完代码必须重建镜像才生效（`docker compose build style-ai && docker compose up -d style-ai`）；镜像构建只跑 `vite build`，**不查前端类型**，`tsc` 要单独一轮。
- 本文档不进镜像（`.dockerignore` 已排除 `**/*.md`）。

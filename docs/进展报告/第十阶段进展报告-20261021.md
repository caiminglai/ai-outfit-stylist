## 二、实现细节（各件为什么是这个形状）

### 2.1 底数（两份盘外只读副本现量，⛔ 均未指活库）

`face_features` **0 行**＝照片识别这条链路一次结果都没落过；`face_profiles` 里 p9 侧 8 行肤色非空 **7**，🔴 而上一条真样本那个人（`user_id=3`）那行**肤色两格逐字 NULL**，同表 `user_id=4` 填了就能出分 ⇒ **卡点是"格子空着"，不是"通路断了"**。另外 `analysis.js:31` 逐字回 **501**（那条自动分析根本没实现），`photos.js:34` 带 `loginRequired` 而推荐入口免登录 ⇒ 上传照片这条路游客第一步就撞 401 ⇒ 所以我没有把取色接到"上传照片走服务器"那条路上。

### 2.2 采样的三条口径（`skinSample.ts`）

- **RGB 各通道取中位数，不是均值**：一颗高光或一片阴影就能把均值拖走；中位数要的是"这块皮肤多数像素是什么"。256 个采样点（框最大 64×64）逐字出现在回执里。
- **默认框＝面部先验框**（画布中间偏上），⛔ 不是人脸检测：零依赖前提下做不到真检测，而"框可以拖"这件事由用户自己完成。显示上限 320 px，原片常 4,000 px，不缩放会吃内存。
- **三道有效性闸门只用 sRGB 通道相对关系**：`r>g>b`（皮肤定义性特征）、`r−b ∈ [8,110]`（要有暖度、又不能是纯橙）、h 闸 `[36.36, 78.05]`、C\* 闸 `[10.53, 30.15]`。⛔ 不用绝对亮度判皮肤，因为亮度正是那张照片最不可靠的东西。

### 2.3 后端只收角度（本轮唯一的架构决定）

请求体新增 `skin_hue`（度）与可选 `skin_hex`（只当视觉回执），**⛔ 永远不接受客户端传来的 Lab**。合成口 `synthesizeSkinLab(toneText, hue)` 在 `colorMetrics.js:1025`（`SKIN_HUE :985`、`skinUndertoneFromHue :1001`、导出 `:1341`）：

```
Lab = { L: 锚点.L,  C: hypot(锚点.a, 锚点.b),  h: 照片实测角度 }
      → a = C·cos(h·π/180), b = C·sin(h·π/180)
非有限数 / 越过 h 闸 / 深浅档名认不出 ⇒ null（缺测不出分，不编肤色）
```

**`L` 与 `C` 逐字取自 C 档手拍锚点表 `SKIN_TONE_ANCHORS`（`:948-957`，八档），照片只贡献角度。** 冷暖切点 52.86／64.02＝CIE TC 1-92 华裔子集（3,555 行／404 人）h° 的 P25/P75，h 闸两侧各外扩 8°＝**C 档手拍**，⛔ 对外不许称"科学判定"。

### 2.4 🔴 取值点是五处不是四处，第五处才是顾客真正看到的那一行

`18` §2.5 我原来写"四处调用点全换成它"——**实测五处**。第五处＝`services/topFromBody.js` 的 `colorSpec()`（现量 `:392`），它只调 `skinToneToLab(value)`、完全不看 `skin_hue`。第一版落地后的现象是：**Top-8 名次改了，顾客看到的建议色逐字没改**。这条洞单测抓不到（那四处都归引擎），**是差分工装抓到的**。现在全仓收敛为"两处消费、一个合成口"（`recommendEngine.js:834`/`:877` 与 `topFromBody.js:38`/`:392`）。

### 2.5 🔴 最贵的一次弯路：照片顶错了格子

第一版我把实测角度顶在**深浅**那颗锚点上，差分回 `A==B true`。概念错位在于 **h° 是冷暖轴、L\* 才是深浅轴**，而处方层两个口径取**低分**（`score = Math.min(...)`），瓶颈恰恰是冷暖那一格 ⇒ 顶错格子＝照片又被瓶颈吃掉。改成"照片顶掉**冷暖**那颗离散锚点（`topFromBody.js:389` `UNDERTONE_WORDS=['冷皮','自然','暖皮']` 命中即跳过、随后追加 `from_photo` 那颗）"，`A==B false` 才成立。这条结论逐字写进了 `topFromBody.js:378-389` 的注释，也写进 `18` §9.2 第 3 条。

### 2.6 界面上"不骗人"的那几个字

组件只在点「用这个」时写档案；按钮文案带「（深浅请自己确认）」；回执一行 `#a88570 · h 57.88° · C 19.40 · 256 个点 · 自然`；提示语「取色只在你手机上算，照片不会上传。方框对准脸颊中间，深浅那一栏请照镜子自己确认」。报告页第 2 层的依据行必须带那条红线：`明度 L 与彩度 C 一律仍取自 C 档锚点表，⛔ 不吃照片的绝对明度`。

## 四、遇到的问题（全部如实，含我自己犯的）

1. **"自动识别肤色"这件事我只做了一半，而且必须只做一半**。Alipour 2026（DOI `10.1111/srt.70374`）实测：非受控照片的 ITA 一致性 **22.9%**，受控基线 **51.3%** ⇒ 从用户随手拍的照片推绝对明度是文献里被否定的一方。现量反例更直接：`#E8C4B8` 经 `hexToLab` 得 **L=81.89**，比华裔子集 P95 还高 16 个点。⇒ 深浅轴留人确认。**代价**：用户如果懒得选深浅，色彩维照样出分但不吃角度（见 §五 第 1 条要你拍的这件事）。
2. **规范自己写错了两处**（就地订正，原文不删）：① "四处调用点"实为**五处**；② `source` 想要 `'archive'` 这一档**实现不了**——`routes/recommend.js:157` 的 `mergeWithArchive()` 把档案并进请求体后只剩一份值，来源标记停在 `used` 数组里、没传进引擎。落地只有 `photo_sample`／`manual`／`null` 三档，不影响出分。
3. **顶错格子那一次**（§2.5）是本轮真正的技术错误，也是我花时间最多的一次：我先怀疑闸门、又怀疑取低分逻辑，最后差分工装一句话把方向钉死（`A==B true`＝处方层根本没被接管）。
4. **前端唯一一条真 bug 是第 7 门抓到的**：`handlePick` 里 `await img.decode()` 在**标签页不可见／后台节流**时永远不 resolve（Chromium 要等"下一次能出帧"），现象＝取色框再也不出现、看着像整页卡死。改成 `load`/`error` 事件＋`img.complete && naturalWidth>0` 兜底。⚠️ 这条**只有真浏览器能发现**，tsc/eslint/build 全绿也照样是坏的。
5. **工装自己踩的两个坑**：① 我原来挂的 5174 自建静态代理**不转发 `/gallery`** ⇒ SPA 把展厅当 iframe 加载、展厅里又是 SPA ⇒ 递归 iframe 把标签页直接卡僵（`navigate_page`/`evaluate_script` 全超时）。正解＝用后端自己发 `app/dist` 的那个实例（日志原话 `[前端] 静态文件服务已启用: app\dist`）。② 测试图我一开始生成的是 **BMP**，被 `UPLOAD_ACCEPT='image/jpeg,image/png,image/webp'` 与 `checkPickedImage` 词表当场挡掉——那道词表是对的，改由 `mk-skin-img.cjs` 手写 PNG（zlib＋自算 crc32，575 B）。
6. **精度上量到一条必须写进文档的抖动**：8-bit sRGB → Lab → 显示色块会让 h 偏 **≈1°**（同一块皮肤屏上显示 57.88°／58°）。⇒ 屏上色块只当视觉回执，判据一律用后端 `photo_hue` 那个原始浮点。
7. **冷暖切点 52.86／64.02 前后端各存一份**（`SKIN_CUT` 与 `SKIN_HUE`）——这是规范 §五a **明知故开**的口子（前端要当场给档名，后端要再判一次），靠钉常数的测试＋盘外 `skin-sample-selfcheck.cjs` 拦漂移，⛔ 不是"已经收敛成一份真相源"。

## 一、②「只填身高体重 → 智能估算」：从建档到进生产链路（第四十三~四十五轮）

### 1.1 为什么先做这个（现量，不是设想）

`backend/services/profileArchive.js:56-71` 的 `BODY_FIELDS` 里 `bust`（胸围，`:59`）与 `shoulder`（肩宽，`:62`）都是**选填**。只填身高体重的档案走到 `topFitBody.bodyDeviation()`（`topFitBody.js:265`）时 `person_cm` 这两格是 `null` ⇒ 松量轴（`:565-593`）与肩缝轴（`:597-618`）算不出 ⇒ `coverage` 掉分 ⇒ 排序层拿不到身体侧算法分。第四阶段的差分里那份档案 `in_pool=0` 就是这笔账（`第四阶段进展报告` §二 档案 D）。

### 1.2 规范先行，再按序写码

按你定的顺序（新算法层先出输入输出规范），规范落在 `docs/依据/13-体型估算输入输出规范-20261020.md`（272 行），八节：输入契约／锚点／三步算法／输出契约／**七条边界禁令**／**10 条已知偏差**／可复算判据／接线落地记录。代码 `backend/services/bodyDimEstimator.js`（372 行）与它同轮写、同轮改。

### 1.3 算法只有三步，但每一步标了它是几档

| 步骤 | 做什么 | 档位 | 依据 |
|---|---|---|---|
| 选表 | 性别 × 年龄 ⇒ 落 GB/T 10000-2023 的哪一张表（男 表 1~4／女 表 6~9） | **A 档**【官方原文·目视抄读】 | 那份 PDF 文本层是废的（U+FFFD 28,263／CJK 0），2026-10-20 用 mupdf `zoom=1.5` 渲染成图后**逐格目视抄**，八张表的表号＋PDF 页＋印刷页逐格登记在 `13` §二，抄读记录在 `10` §1m |
| 估胸围 | `bust = 该表胸围 P50 × (这个人 体重/身高 ÷ 该表 P50 同行比值) ^ 0.69` | 锚点 **A 档**、**指数 0.69 是 C 档·本站自拟** | 🔴 GB/T 10000-2023 全文**没有任何**"身高＋体重→胸围"的回归式或换算表，它给的是每个部位各自的人群**边缘**分布、部位之间不配对 ⇒ 国标在这里只能当锚点与钳位框，给不了斜率。0.69＝把 8 表 × 7 档＝56 格喂进 minimax 拟合、按 **0.001 步长**重扫出来的最优值（最大绝对残差 1.92%，次优 0.68→2.11%、0.70→2.27%）；工装 `render/fit-check.mjs` |
| 估肩宽 | `shoulder = 该表肩宽 P50 + 斜率 × (胸围 − 胸围 P50)`，斜率男 0.30／女 0.25 | 斜率 **A 档**，跨口径使用是本站的取舍 | 斜率借 GB/T 1335 附录 B 表 B.1 的「总肩宽」分档增量（男 +1.2÷4、女 +1.0÷4，【官方原文·文本层逐字】，男册 PDF p10／女册 p8）。⚠️ 1335 的「总肩宽」按 GB/T 16160-2017 §2.2.5 是肩峰点间**水平弧长**，与 10000 的「肩宽」（GB/T 5703-2023 §6.2.7 直线距离）同一个人差 3~5 cm ⇒ **只借斜率、绝对值绝不互换** |
| 钳位 | 两层框取更紧的一侧：本表 P1/P99 ＋ 肩宽÷身高 `[0.21056, 0.23542]` | 框**不是第三个手拍常数**，由同一批锚点现算 | 44 个"同表同分位"配对点的范围；⛔ 这一框不给胸围加（胸围吃脂肪，同档配对里胸围÷身高跨 47.4%~64.9%，加了会把偏胖的人压回人群中间值，那正是合身层要避开的事） |

## 二、①「门店扫码快速录入」：扫码枪一次键入带出六格（第四十六轮）

### 2.1 你拍的三个口径（本轮按此实现，没自做主张）

### 2.2 数据结构：一列、三条不做什么

`schema.sql` 的 `CREATE TABLE` 与 `backend/db/init.js:139-142` 的 `MISSING_COLUMNS` 各加一条 `['user_wardrobe', 'sku', 'TEXT']`。

- ⛔ **不设 DEFAULT**：`NULL` ＝ 这件不是扫来的（与第二阶段那四格实测尺寸同一口径）。
- ⛔ **不建唯一索引**：同一人可以有两件同款、游客还共用会话，唯一索引会把第二件直接顶掉。
- 索引 `ix_user_wardrobe_sku`（普通）**只在 `init.js:180-181` 补列之后建**，`schema.sql` 里不放——老库跑到那一行时列还没补上会直接报错（与 `ix_rule_groups_source_key` 同一套路）。

### 2.3 新读口：`GET /api/wardrobe/sku`（`routes/wardrobe.js:550`）

一次扫描要同时问两张表，因为"这件我有没有"和"这件是什么"是两个问题：

```sql
-- ① 我自己衣柜里有没有（按会话隔离，别人的码不串到我这）
SELECT * FROM user_wardrobe WHERE session_id = ? AND sku = ? ORDER BY created_at DESC
-- ② 门店库存里有没有（只认上架，带出分类 code 给前端预填）
SELECT p.id, p.name, p.sku, ..., c.code AS category_code
  FROM inventory_products p LEFT JOIN inventory_categories c ON p.category_id = c.id
 WHERE p.sku = ? AND p.enabled = 1 ORDER BY p.created_at DESC LIMIT 20
```

回 `{sku, mine[], store[], in_wardrobe, in_inventory}`。**参数缺失**在路由里是 400，但真实链路上先被路由外的 `loginRequired` 拦掉（`middleware/auth.js:69`）⇒ 无会话实测回 **401**（本轮 API 探针第一次按 400 断言、实测纠正为 401，判据按链路写）。

### 2.4 写入口：两格同一个文本口径

`POST` 落 `asText(data.sku) || null`（`:527`）、`PUT` 的 `sku`／`image_url` 各一支 `val = asText(raw) || null`（`:703-708`）。`asText`（`utils/common.js:132-136`）把非文本归成 `''`，空串再落 `NULL` ⇒ `{}`/`[]` 这类真值不再一路绑进 SQLite 抛 `RangeError` 换一句 500。**这一条同时修掉了 `image_url` 上原本就存在的同一个洞**（原来写的是 `data.image_url || null`）。

### 2.7 这一项遇到的问题

1. 🔴 **扫码查重不分店**：`inventory_products` 根本没有 `store_id` 这一列（全仓 `CREATE`/`ALTER` 现量 **0 处**）⇒ 多家店共用一张库存表时，A 店能扫出 B 店的同款。要不要按分店记账＝**等你拍板**（它是个结构变更，不是补个 WHERE 就行）。
2. ⚠️ **`inventory_products.sku` 没有唯一索引**：同码多条并存时前端取最新一条并在提示里写明"同码有 N 条，取最新一条"（`WardrobeTab.tsx:420`），但后台录入门禁没有查重闸门 ⇒ 脏数据会一直累积。
3. ⛔ **摄像头识码没做**：手机摄像头扫 QR／条码要引入解码依赖（jsqr 一类）＝新依赖，按"掏钱/新依赖需你点头"的规矩没装。现状＝**手动或扫码枪**；手机端可用「拍照」那条链路先存图（§三）。
4. ⚠️ 扫码枪这一路的真实前提：设备得把它当键盘输入（绝大多数如此，回车后缀是默认配置），且**浏览器焦点要在输入框里**。本轮没做的是失焦自动聚焦（多数扫码枪场景不需要，但门店里顾客点了别处就会扫空）——留作观察项。

## 三、③「数据采集／上传照片」：先把谎报的那条改掉（第四十六轮）

### 3.1 现量到的洞（这是本轮最该报的一笔）

`WardrobeTab.buildPayload`（`:330` 一带）**从来没发过 `image_url`**。链路是：点「📷 拍照上传」⇒ `POST /api/clothing/upload` 把文件写进 `uploads/`、插一行 `clothing_items`、回 `image_url` ⇒ 前端 `handlePhotoUpload` **把这个地址丢掉** ⇒ `user_wardrobe.image_url` 恒 `NULL`。而 toast 写的是"照片已保存"。⇒ **数据一直在录，但录到的是"没照片的服装"**，顾客和后台都看不出来。查法：`SELECT COUNT(*) FROM user_wardrobe WHERE image_url IS NOT NULL` ⇒ 本机 dev 库 **0**。

### 3.2 修法：六处接通＋一条同源渲染守卫

| 处 | 行号 | 做什么 |
|---|---|---|
| 表单默认值 | `WARDROBE_FORM_DEFAULT` 加 `image_url: ''` | 与其余文本格同形状 |
| 回填 | `openEdit`：`image_url: item.image_url ??` | 改一件时不把已有图冲掉 |
| 发值 | `buildPayload`（`:330`）：`image_url: form.image_url.trim() || null` | 洞的正解：把地址真发出去 |
| 写入 | `handlePhotoUpload`（`:465`）：`image_url: result.image_url` | 上传回来就落到这一件上 |
| 扫码 | `:415`：`image_url: p.image_url ?? ''` | 后台给这件商品传过图就直接带出来，不重复上传 |
| 展示 | 表单预览 `:813`＋卡片 `:885`，都走 `sameOriginImage()`（`:48`） | 只认同源 `/…` 且排除 `//`；外部地址**不请求**、值仍留库 |

守卫这条不是装饰：`image_url` 这一格后台是**自由文本**，顾客侧一旦 `<img src>` 原样渲染外部地址＝让每一个顾客浏览器替那个站点发一次请求（追踪像素、在线状态、点击计数都可能）。店员侧不是顾客侧，风险等级不一样。
